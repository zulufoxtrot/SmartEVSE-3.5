# AGENTS.md

Guidance for agents working on this repository. SmartEVSE-3.5 is an ESP32 firmware
for an EV charger (EVSE) with an attached CH32V203 coprocessor. Project root for
builds is `SmartEVSE-3/`; everything PlatformIO-related lives there.

## Build Commands
All commands run from the PlatformIO project directory, not repo root.

- Build v3 (ESP32, default env): `cd SmartEVSE-3 && PLATFORMIO_BUILD_FLAGS='-DDBG=1 -DMIN_CURRENT=5' pio run`
- Build v4 (ESP32-S3): `cd SmartEVSE-3 && pio run -e v4`
- Build CH32V203 coprocessor: `cd SmartEVSE-3 && pio run -e ch32` (also run automatically as the first pre-script of the v4 env)
- Flash over USB: `cd SmartEVSE-3 && pio run -t upload` (preferred — also reflashes bootloader + partitions)
- Build artifacts: `SmartEVSE-3/.pio/build/<env>/firmware.bin` (there is a `SmartEVSE-3/release` symlink to `release/`)
- `DBG` levels: `0` = no logging (default), `1` = telnet debug server over WiFi, `2` = log to USB-C

## Pre-build Scripts (run automatically — do not skip)
Configured via `extra_scripts` in `SmartEVSE-3/platformio.ini`. All of them shell out
to `python`, so `python` (not just `python3`) must be on PATH; on Linux symlink
`/usr/bin/python3 -> /usr/bin/python` if needed.

- `packfs.py` — minifies `data/index.html` and `data/styling.css`, gzips the rest of
  `data/*`, and writes `SmartEVSE-3/src/packed_fs.c` (mongoose packed FS blob).
  `packed_fs.c` is **generated**; never edit it by hand and do not commit it
  (already in `.gitignore`).
- `replace_mbedtls.py` — swaps in custom mbedTLS static libs from
  `SmartEVSE-3/custom_libs/esp32/` (and `esp32s3/`) to save ~22KB RAM per TLS
  connection; backs up originals with `.original` once.
- `make_ch32.py` — **v4 only**, runs before `packfs.py`: builds the ch32 env and
  copies the result into `data/CH32V203.bin` so the ESP32 can flash the CH32
  coprocessor at runtime. `packfs.py` then cleans this file up after packing.
- `gen_ldscript.py` — ch32 env only, generates the linker script from
  `ch32v003fun/ch32v003fun.ld`.

## Environments
Defined in `SmartEVSE-3/platformio.ini`:

- `release` (default; v3 ESP32, `SMARTEVSE_VERSION=30`) — board `esp32dev`,
  partitions `partitions_custom.csv` (1.7MB OTA slots, no coredump).
- `v4` (ESP32-S3, `SMARTEVSE_VERSION=40`) — board `esp32-s3-devkitc-1`,
  partitions `partitions_custom_v4.csv` (3.5MB OTA slots + coredump),
  has PSRAM and a CH32 coprocessor.
- `ch32` (CH32V203 coprocessor, no `SMARTEVSE_VERSION` defined) — uses
  `https://github.com/Community-PIO-CH32V/platform-ch32v`, `wch-link` upload.

Use `#if defined(SMARTEVSE_VERSION) && SMARTEVSE_VERSION >= 40` (or `>= 30 && < 40`)
to gate v3/v4-only code; `#ifndef SMARTEVSE_VERSION` means CH32. Many headers in
`SmartEVSE-3/src/` already follow this pattern (`esp32.h`, `modbus.h`, `meter.h`, …).

## Code Style
- 4-space indentation, no tabs.
- PascalCase for globals (`MaxMains`, `GridRelayMaxSumMains`) and functions
  (`CheckSwitch`, `handleWIFImode`).
- Comments: `//` inline, `/* */` blocks. Some files use a leading `;` on comment
  lines (legacy from assembler/asm-style headers).
- Headers use `#pragma once` or include guards.

## Project Structure
- `SmartEVSE-3/` — PlatformIO project root (`platformio.ini` here).
- `SmartEVSE-3/src/` — main sources. Notable files:
  `main.cpp`/`main.h` (entrypoint), `evse.c` (EVSE state machine),
  `esp32.cpp` (WiFi/MQTT/REST), `network_common.cpp` (webserver + OCPP),
  `glcd.cpp` (LCD), `modbus.cpp`, `meter.cpp`, `OneWire*.cpp` (sensor),
  `mongoose.c` (vendored), `packed_fs.c` (generated, gitignored).
  `glcd.cpp` includes `font.cpp` (5x8), `font2.cpp` (~10x16) and the generated
  `font3.cpp` (compact 5x16 double-height, used by the SMART/SOLAR power
  display). `font3.cpp` is generated by `gen_font3.py` at repo root — edit the
  generator, not the file.
- `.opencode/skills/smartevse-upload/` — skill + `upload.py` helper for OTA
  uploading firmware to a controller over its `/update` HTTP endpoint
  (default controller: `10.0.0.91`).
- `SmartEVSE-3/data/` — web UI assets (HTML/CSS/keys) served by the device.
  Edit these, not `packed_fs.c`.
- `SmartEVSE-3/lib/RemoteDebug/` — local copy of RemoteDebug; only used by the
  `debug.h` macros, not the main webserver.
- `SmartEVSE-3/test/` — hardware-in-the-loop test scripts (see below).
- `SmartEVSE-3/custom_libs/` — patched mbedTLS `.a` files. Rebuild needed only if
  you bump the `espressif32` platform version.
- `docs/` — `building_flashing.md`, `configuration.md`, `REST_API.md`, `ocpp.md`.
- `integrations/` — Home Assistant YAML and ESPHome YAML examples.
- Root-level `src/`, `include/`, `lib/` are empty PlatformIO scaffolding
  (READMEs only) — do not put code there.

## MQTT
- Default topic prefix is `SmartEVSE/<4-digit-serialnr>/` (set in
  `network_common.cpp:2325`); the device hostname `smartevse-xxxx` is the same
  4-digit serial. Example: `SmartEVSE/51446/Set/Mode`.
- The prefix is user-configurable via the web UI (param `mqtt_topic_prefix`),
  so do not hardcode it — always go through the `MQTTprefix` global.
- Set topics live under `…/Set/<Name>`; see the long list in
  `docs/configuration.md` (Mode, CurrentOverride, MainsMeter, EVMeter,
  HomeBatteryCurrent, RFID, …).
- Home Assistant auto-discovery messages are published under
  `homeassistant/<domain>/<prefix>-<entity_suffix>/config` on connect.

## REST API
- Base URL: `http://<ip-or-smartevse-xxxx.local>`. Full spec in `docs/REST_API.md`.
- GET = read (e.g. `/settings`); POST = write. POST requests **must** end with
  `-d ''` — the Mongoose webserver will otherwise hang waiting for body data.
- For automated tests there is a hidden `/automated_testing?...` endpoint
  guarded by `DAUTOMATED_TESTING=1`.

## Testing
There is no unit test framework wired in. `SmartEVSE-3/test/` is a
hardware-in-the-loop harness that drives one master + one slave SmartEVSE on a
test bench. **Do not run these against a live installation** — the script
itself warns it will trip breakers.

- Build firmware with `-DAUTOMATED_TESTING=1` to expose the test endpoints.
- `test/tests.sh <master-serial> <slave-serial> <test-bitmask>` — bitmask selects
  which test(s) to run; pass `0` for all. Requires `jq` and a `mosquitto` broker.
- `test/feed.sh`, `feed_mains.sh`, `feed_ev.sh`, `feed_bat.sh`, `feed_circuit.sh`
  — interactive feeders that publish to `SmartEVSE/<serial>/Set/MainsMeter`
  and `…/Set/EVMeter`.

## CI / Release
- `.github/workflows/pio-build.yaml` — builds both a normal and a debug
  `firmware.bin`, then **signs each with the RSA key in `SECRET_RSA_KEY`** and
  appends the signature to produce `firmware.signed.bin` / `firmware.debug.signed.bin`.
  These signed blobs are what end users flash.
- `.github/workflows/pio-release.yaml` — runs on `v*` tags, calls the build
  workflow, and uploads the artifact zip to the GitHub release plus an S3 bucket
  (`smartevse-3/` in `eu-west-2`).
- Build-time version is set via `-DVERSION=\"v<x.y.z>\"` in
  `PLATFORMIO_BUILD_FLAGS`.

## Quirks / Gotchas
- `packed_fs.c` regenerates on every build from `data/`; do not check it in.
- Custom mbedTLS libs are version-locked to `espressif32 @ 6.10.0` — bumping
  the platform may require rebuilding `custom_libs/esp32*/*.a`.
- v4 firmware embeds the CH32 coprocessor binary in its SPIFFS image, so a
  successful v4 build always runs `make_ch32.py` first. A bare `packfs.py` on
  v4 will fail because `data/CH32V203.bin` is missing.
- OTA: v3 firmware must be flashed to both partitions `0x10000` and `0x1c0000`
  for A/B swap; v4 uses `0x10000` and `0x390000` (see `partitions_custom*.csv`).
- `coredumping.txt` is a personal cheat-sheet for reading coredumps from the
  v4 coredump partition — not a build step.
