# SmartEVSE OTA firmware upload

Upload a freshly built SmartEVSE firmware to the controller over WiFi using
the device's built-in `/update` HTTP uploader. No USB cable needed.

## When to use

- The user asks to upload / flash / deploy the firmware to the controller.
- The controller is reachable over the network (here: `http://10.0.0.91`).
- A local `firmware.bin` needs to be pushed instead of using the web UI's
  "Choose file..." button.

## How the upload works

The SmartEVSE webserver does **not** accept a single large POST and it does
**not** use `multipart/form-data`. It implements a chunked uploader at
`/update` (see `SmartEVSE-3/src/network_common.cpp`):

- Every request is a `POST` whose **raw body is one 8192-byte chunk** of the
  binary.
- Query parameters are mandatory:
  - `offset` = byte offset of this chunk in the file
  - `file`   = the logical filename. ONLY `firmware.bin`, `firmware.debug.bin`,
    `firmware.signed.bin`, `firmware.debug.signed.bin` (and `rfid.txt`) are
    accepted — any other name returns `400 only allowed to flash ...`.
  - `size`   = total file size in bytes.
- The file must be ≤ `0x1B0000` bytes (partitions_custom.csv limit).
- When `offset + body == size`, the device calls `Update.end()`, verifies, and
  reboots.

## Procedure

1. **Build** the firmware (run from `SmartEVSE-3/`, the PlatformIO root):

   ```
   cd SmartEVSE-3 && pio run
   ```

   Default env is `release` (v3, ESP32). Output:
   `SmartEVSE-3/.pio/build/release/firmware.bin`
   For the ESP32-S3 v4 board: `pio run -e v4`.

   Do not commit `SmartEVSE-3/src/packed_fs.c`; it is regenerated by
   `packfs.py` on every build. The pre-build scripts need `python` on PATH.

2. **Upload** the binary with the helper script:

   ```
   python3 .opencode/skills/smartevse-upload/upload.py
   ```

   Options:
   - `--host 10.0.0.91` (default) — controller IP or hostname.
   - `--file path/to/firmware.bin` — overrides the default build artifact.
   - `--chunk 8192` — chunk size (matches the built-in web UI).

   The script sends all chunks, prints progress, and waits for the device to
   finalise the OTA. The controller reboots itself on success.

3. **Verify**: after ~10-30 s, poll the controller, e.g.
   `curl http://10.0.0.91/settings` or open `http://10.0.0.91` in a browser.
   The version shown should match the build. If the webserver is slow to come
   up, just wait — the update link is usually the first thing to respond.

## Notes / gotchas

- **Name must be exact**: the query param `file=` must be one of the allowed
  names. The helper maps an arbitrary local `*.bin` to `firmware.bin`.
- **Unsigned vs signed**: locally compiled builds are unsigned, so upload as
  `firmware.bin`. Signed release builds (from CI) use `firmware.signed.bin`.
- **HTTP only**: the update form works over plain HTTP; HTTPS clients will
  fail (the server is plain HTTP on port 80 anyway).
- **Don't interrupt**: killing the upload mid-way leaves a partial OTA. The
  device boots the old partition if verification fails, but re-run the full
  upload to be safe.
- **rfid.txt**: bulk-upload RFID tag lists via the same endpoint with
  `file=rfid.txt` (uploaded in one shot, not chunked OTA).

## Manual equivalents

One-shot equivalent for a small file (offset 0, size = file size):

```
curl -X POST --data-binary @firmware.bin \
  "http://10.0.0.91/update?offset=0&file=firmware.bin&size=$(stat -f%z firmware.bin)"
```

Use the Python helper for anything bigger than ~1 MB — the ESP32 webserver
can choke on a single huge body.
